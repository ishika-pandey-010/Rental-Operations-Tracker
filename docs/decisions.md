# Decision log

One line per decision: what, why, and what we gave up. Newest at the bottom. A decision is changed by adding a new row that supersedes the old one, never by editing it.

| ID | Date | Decision | Why | Trade-off / alternative rejected |
| --- | --- | --- | --- | --- |
| D-01 | 2026-10-15 | Next.js + Supabase (Postgres, Auth, RLS) on free plans | Postgres constraints and RLS let the database enforce the money rules; free hosting for a public demo | Supabase free projects pause when idle → seed script and ping before demos (R-11) |
| D-02 | 2026-10-15 | Store money as `bigint` cents | Floats can't represent 0.10 exactly; integer cents make sums exact | Display code must format cents; one currency only |
| D-03 | 2026-10-15 | Append-only ledger: corrections are reversals and adjustments | A ledger you can edit can't be trusted or audited; common practice in rent-ledger design (see competitive analysis) | More rows; the UI must show reversed items clearly |
| D-04 | 2026-10-15 | Prorate by actual days in the month, half-up to the cent | Simple to explain to a tenant; matches the calendar | Some jurisdictions use a 30-day month (e.g. California guidance); revisit if discovery shows target users need it (PRD Q1) |
| D-05 | 2026-10-15 | Rent lives in an effective-dated `lease_rent_schedule`, not one `monthly_rent` column | A mid-lease rent change must not rewrite past charges (FR-07) | One extra join when generating charges |
| D-06 | 2026-10-15 | Charge generation is idempotent: partial unique index + `ON CONFLICT DO NOTHING` | A retried or double-clicked job must not bill twice (P1) | None worth noting |
| D-07 | 2026-10-15 | Payments allocate oldest-first by default; credit auto-applies to the next charge | Matches how landlords think ("pay off what's oldest"); fewer clicks | Landlord must use manual override for unusual cases |
| D-08 | 2026-10-15 | Deposits, deductions and refunds are separate tables, never rows in the rent ledger | Deposits are held money, not income (P3) | Two places to look; the lease page shows both |
| D-09 | 2026-10-15 | Deductions above the deposit become a `deposit_shortfall` charge, never a negative refund | A negative refund is meaningless; the tenant owes money, which the ledger already handles | `charges` needs a `kind` column, so the unique rule is a partial index on `kind = 'rent'` |
| D-10 | 2026-10-15 | A renewal is a new lease linked to the old one | Keeps each term's dates and rent schedule clean; history stays intact | Two leases per tenancy in reports; grouped by `renewed_from_id` |
| D-11 | 2026-10-15 | One landlord per account; `owner_id` on every table drives RLS | Simplest model that fits the persona | No shared access for a second manager in v1 |
| D-12 | 2026-10-15 | Late fees and maintenance work orders are out of v1 | Similar products include them, but they don't address P1–P5 and late-fee rules vary by jurisdiction | Less feature parity with competitors (see competitive analysis) |
| D-13 | 2026-10-15 | Docs are the primary deliverable; every artifact uses stable IDs and a traceability matrix | This is a PM portfolio piece: a reviewer must be able to follow FR → US → TC → R in under a minute | Extra upkeep each time a story changes |
| D-14 | 2026-10-15 | Sprint board and bugs in Jira; GitHub issue templates mirror the same fields | Jira is what PM roles expect to see; GitHub keeps a public copy reviewers can open | Two tools to keep in sync; Jira is the source of truth |
| D-15 | 2026-10-17 | Build S1–S3 in one run without pausing for plan or migration approval | The owner asked for the whole build in auto mode. Plans still go in `docs/sprint-plan.md` and each migration lands in its own reviewed commit before the code that uses it (OQ-01) | Supersedes the "wait for OK" part of CLAUDE.md working rules 2–3 for this build. A wrong call costs a follow-up migration instead of a conversation |
| D-16 | 2026-10-17 | Start S1 before the G0 → S1 gate (discovery, PRD review, testers booked) | The owner asked for the build to start; discovery needs real people and can't be done by Claude (OQ-02) | Discovery may cut a problem after code exists. Each money rule is its own constraint or trigger, so a cut rule is one small migration. Tracked as R-15 |
| D-17 | 2026-10-17 | Work on `feature/…`, `bug/…` and `chore/…` branches cut from `dev`, merged into `dev` with `--no-ff` and pushed; `main` changes only at release | The owner asked for branches integrated continuously into `dev`. The GitHub CLI account here has read-only access, so PRs can't be opened; merge commits keep each branch visible in `git log --graph` | No PR review threads on GitHub. Each merge commit message carries the IDs a PR title would |
| D-18 | 2026-10-17 | `docs_check.py` reads TC IDs from test names and `US-nn` tags from code comments, and writes the test and code columns of `traceability.md` | The build prompt wants each test linked to its requirement and code; CLAUDE.md forbids hand-editing the matrix (OQ-03). Generating both keeps one source of truth | Test names must start with the TC ID they automate. A test with no TC ID still runs but doesn't appear in the matrix |
| D-19 | 2026-10-17 | Next.js 15.5 (maintained 15.x line), not 16 | 15.5 is the newest line with the App Router and `middleware.ts` API this build was planned around; it still gets security backports | Misses Next 16 features; an upgrade is a later chore |
| D-20 | 2026-10-17 | A `refunds` row records a refund being paid and is never edited; `pending` is derived (ended lease, deposit held, no refund row) | NFR-04 says statuses are derived. A stored `pending → paid` status would be the only hand-set status in the schema (OQ-13) | Changes data-model.md: `refunds.status` is gone; "mark paid" inserts the row. Deductions and deposits lock once the refund is paid |
| D-21 | 2026-10-17 | Child tables reference parents by `(id, owner_id)` composite foreign keys | RLS checks only the row being written. Without this, landlord B could insert a deposit with B's `owner_id` that points at A's lease (US-02 AC3) | Every parent needs a `UNIQUE (id, owner_id)` and every FK has two columns |
| D-22 | 2026-10-17 | Money operations (create lease, generate charges, record payment, reverse, move out, refund) are Postgres functions called over RPC; the Next.js code formats and submits | The rules must hold for any client, including the SQL editor. One place for the arithmetic means TypeScript never adds cents (CLAUDE.md money rules) | More SQL to maintain; errors raised in SQL must be worded for the landlord, so the wording lives in migrations |
| D-23 | 2026-10-17 | The first month's due date is the later of the due day and the lease start | A 2026-11-16 move-in with due day 1 would otherwise be overdue before the tenant arrived (OQ-12) | Tightens US-11; logged rather than silently assumed |
| D-24 | 2026-10-17 | Payment reference is optional; when given it is unique within the lease | Cash and some cheques have no reference, and a forced made-up reference would defeat the duplicate check (OQ-11) | A cash payment entered twice isn't caught by the reference rule |
| D-25 | 2026-10-17 | Currency is a display setting (`NEXT_PUBLIC_CURRENCY`, demo USD); there's no currency column | PRD §8: one currency per account. Cents are currency-free (OQ-06) | A landlord can't pick a currency in the app; changing it is a deploy setting |
| D-26 | 2026-10-18 | Every money function takes `pg_advisory_xact_lock` on the lease before reading balances; the allocation trigger takes the same lock | Under READ COMMITTED, two transactions can each see the old total and both pass a "sum ≤ amount" check. Serialising per lease closes that gap without serialising the whole database | Concurrent writes to one lease queue behind each other; for one landlord that's milliseconds |
| D-27 | 2026-10-18 | Charge generation covers ended leases up to their move-out date, and the charge amount is worked out from the move-out date when there is one | If a move-out is recorded before the month is generated, the month must still be charged, prorated (US-09 AC1, TC-LEASE-12) | A lease ended by mistake can't be "un-ended"; the trigger forbids going back |
| D-28 | 2026-10-18 | `purge_account(owner)` is the only way ledger rows are ever deleted; service role only; it marks its transaction with the owner and `reject_ledger_change()` lets that owner's deletes through | NFR-09 needs the demo account rebuilt in one command, and append-only tables (NFR-02) otherwise refuse every delete, even from the database owner | A single, tested exception to "never deleted". The alternative, truncating every table, would wipe every account on a shared demo database |
